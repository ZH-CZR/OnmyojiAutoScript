## 4. P0：先消除资源与状态损失

### 4.1 流火阵容站位冲突

**现状与依据**：`strategy/lineup_strategy.py::LIUHUO_CONFIG` 中，天火命铃彦姬和梦山白藏主均为7号位。`build_lineup_shikigami()` 验证位置范围，但不禁止不同式神使用同一位置。上阵后按名称追加名单及位置，没有完整的互斥替换声明。

**风险**：实际出现替换或交换时，内部仍可能认为两者均在原站位，影响人数、装备目标和后续补位。

**方案**：

1. 明确二者是否设计为同时上阵；若是，分配独立且经确认的站位，不凭空指定“最佳位置”。
2. 构建阵容时默认禁止重复站位，错误信息包含阵容名、位置和冲突式神。
3. 若确需替换，显式声明替换关系、触发条件和替换后的名单变化，不能以重复位置隐式表达。
4. 上阵确认除手牌减少外，增加目标位置身份或可信棋盘变化证据；发生交换时同步原单位的新位置或下场状态。

**验收**：所有阵容唯一站位检查通过；重复位置会明确报错；替换后每个位置最多一个普通单位，装备目标与实际占位一致。

### 4.2 刷新确认与“结果未明”状态

**现状与依据**：`runtime/economy.py::_click_shop_refresh_and_confirm_slots()` 以至少三个槽位变化确认刷新成功，未满足时可再次点击。对应槽位前后都识别出同名时，即使已经重新生成，也视为未变化。

**风险**：有效刷新恰好保留多个同名槽位，或动画/OCR延迟导致变化不足，会再次花钱并跳过第一轮新牌。当前尚无实测证据说明发生频率。

**方案**：

1. 一次动作只发出一次刷新点击，记录点击前金币、五格身份、图像特征、回合和阶段。
2. 分开表达“扣款已发生”和“新商店已稳定”，不得只凭金币下降就立即扫描购买。
3. 综合稳定的费用变化、卡面变化和刷新动画结束判断结果；期间出现回合收入、折扣或其他资源变化时降低证据可信度。
4. 卡面变化数量只作辅助证据，不作为必须达到三个的硬条件。
5. 结果未明时进入有界等待，禁止立即重刷；确认新商店稳定后先扫描买卡，再允许下一次刷新。
6. 只有明确证据表明动作未发生时才允许重试。阶段变化或超时则停止本轮操作，并重新观察。

**验收场景**：五格完全相同、仅一到两格变化、OCR暂时失败、卡面动画延迟、点击未生效、点击后收店、刷新时跨回合、资源效果干扰。前几类场景不能因未达到三格变化而产生第二次付费点击。

### 4.3 满手保护与腾位闭环

**现状与依据**：`sell_one_lineup_hand_card()` 在兜底时出售最右侧已识别阵容卡；没有读取待购卡价值进行比较。购买后目标仍在商店，也未必足以证明手牌确实已满。

另一个需一并处理的接口问题：`emergency_cleanup_hand()` 允许备、战两阶段，但调用 `_ensure_shop_closed()` 时没有传阶段，后者默认只允许备阶段，因此战阶段腾位会受阻。修复时需区分战阶段允许卖卡与是否允许装备，不能简单放开全部操作。

**方案**：

1. 先确认购买受阻原因：动画、未生效、金币不足、阶段切换、手满分别处理。
2. 在合法阶段依次尝试使用可安全处理的物品、上阵可立即使用的单位、出售已确认的低价值卡。
3. 决策显式接收待购卡，比较“新卡提升”与“腾位损失”；不值得交换时跳过购买。
4. 未识别卡、关键升级材料、尚未上场的唯一核心，默认受到保护；状态不确定时不得凭位置出售。
5. 售出后确认数量减少，重新打开并识别商店，检查原目标是否仍在，再购买。

**验收**：不会卖掉受保护材料换普通补件；无安全出售目标时能够放弃购买；战阶段可合法腾位且不会触发备阶段专属拖动。

## 5. P1：建立一致的持牌与资源价值判断

### 5.1 最小状态模型

建议先建立任务内存中的观察状态，候选字段如下；这些字段尚未全部实现。

| 状态 | 用途 | 不可用时的处理 |
| --- | --- | --- |
| 回合、阶段、剩余时间、帧标识 | 判断动作是否合法及是否来得及 | 停止新破坏性动作并重读 |
| 金币、等级、经验进度、当前费用 | 预算与升级判断 | 不猜测扣款或升级收益 |
| 场上单位、实际站位、星级、装备 | 计算即时战力和装备目标 | 保留最近可信状态并标记过期 |
| 手牌身份、数量、星级及空位 | 升星材料与腾位选择 | 不卖可能重要的未知卡 |
| 商店五格身份、价格与置信度 | 购买优先级 | 重读；禁止刷新越过未确认交易 |
| 实际羁绊、已选符咒 | 评估边际收益 | 不把计划阵容视为已成型 |
| 血量、近期掉血及对手信息 | 风险运营与后期站位 | 使用保守规则，不凭空推断 |

同一张截图中的稳定识别结果可复用；点击、拖动、买卖、升星或切换阶段后必须失效相关缓存。不同帧数据组合时保留时间与可信度，不能伪装成同一时刻的完整状态。

购买次数不能直接等同于当前持有数量：合成、赠送、出售及系统自动上阵均可能改变状态。需在关键动作后重新核对。星级规则未确认前不写死合成数量。

### 5.2 统一买卡评分

当前 `buy_lineup_shikigami_from_shop()` 按槽位顺序购买目标卡，只判断是否属于阵容及是否买得起。

建议先采用可解释的分层规则，而非立即堆叠难以校准的数值权重：

1. 立即完成关键主力升星。
2. 立即补齐有效羁绊或填补重要空位。
3. 主力核心及受保护升级材料。
4. 普通体系补件。
5. 远期追星材料及低收益重复卡。

同层再比较本轮能否上场、价格、当前持有数量、手牌占用和经济损失。每次购买完成后重新评估剩余目标，不能一直执行旧排序。

新增“持有目标”而非无条件购买名单：区分追星核心、仅需要一份的挂件和暂时保留的过渡卡。最高星级、额外持有收益及购买上限应基于已验证规则。

保留金币应由统一预算接口解释：关键即时提升可按策略突破保留线；低价值材料需遵守储备约束。避免升级刷新存钱、买无关紧要的重复卡却随意花光的割裂行为。

### 5.3 卖卡评分

出售顺序应依次考虑：明确无用的非体系卡、过渡完成后的替补、超出持有目标的材料、确认收益较低的远期备牌。

硬保护包括未知高风险卡、唯一核心及即将形成关键升级的材料。只有在状态明确且策略解释充分时才允许突破保护；日志必须说明原因。

“最左/最右”只可作为价值完全相同时的稳定排序方式，不能充当价值判断。

### 5.4 发现选项与装备分配

**现状与依据**：`discover_souls_from_hand()` 使用 `random.choice(options)`；`_soul_targets()` 在专属规则之外主要按站位奇偶分配；专属目标未上场时可回退给普通目标；`_emblem_targets()` 主要按站位升序选择目标。

**方案**：

- 识别发现界面的三个具体选项，不仅识别三个选择按钮。
- 阵容声明主输出、主坦、辅助、过渡角色及装备优先级。
- 区分“必须为核心保留”“允许过渡使用”“普通兼容”三种装备策略。
- 按实际装备空位、已有装备、可用目标和本轮提升选择御魂。
- 纹章先比较是否跨越有效羁绊档位，再比较携带者适配度和装备槽机会成本。
- 若装备不能安全回收，不设计未经验证的临时装备再转移流程。
- 选项识别失败时有界重读；仍失败时采用明确记录的兜底，不宣称已经选到最优项。

**验收**：关键装备有目标时优先选取；同名重复装备不错误占槽；满装目标被跳过；核心未上场时保留策略生效；纹章不因站位靠前而占用更重要的装备位置。

## 6. P2：动态经济与过渡阵容

### 6.1 四种运营状态

| 状态 | 典型触发证据 | 行为 |
| --- | --- | --- |
| 积累经济 | 场面稳定，无明确即时提升 | 减少低收益刷新，保留储备 |
| 提高质量 | 关键对子多、主力质量不足 | 在预算内搜索核心升级 |
| 提升人口 | 升级后有可立即上场的关键单位 | 优先达到下一有效人口节点 |
| 紧急保命 | 血量及近期损血显示风险，识别可信 | 降低储备，优先当前回合提升 |

状态切换必须带原因，并使用稳定确认或滞回规则，避免单帧血量/OCR抖动导致存钱与花钱反复切换。

血量尚未接入时，可以先根据空位、升级后可上场单位、关键对子和主力完成度优化；此时不得宣称策略已经具备保命判断。

### 6.2 升级与刷新决策

每次动作前回答：

1. 当前商店是否还有更值得购买的卡？
2. 买经验距离实际升级还差多少，升级后能上什么？
3. 刷新主要寻找谁，是否还有追求目标？
4. 本轮剩余时间是否足够购买并兑现战力？
5. 花费后是否破坏需要保留的经济档位？

目标人口应成为阵容的显式策略参数，与候选名单长度分离。加入过渡卡、替补后，不能因为名单变长而提高目标等级。

达到目标人口后仍需判断核心完成度、经济状态及剩余提升空间，不再直接将储备设为零。临近危险时可以集中花钱，但需要明确局势证据。

费用和收益需考虑实际符咒效果。现有4金币经验、2金币刷新是当前常量；引入动态策略前需核实哪些效果会改变费用、经验或收入。读取不可靠时不得因此反复点击试探。

### 6.3 有限过渡阵容

每套阵容分别声明：

- 前期允许保留的过渡卡。
- 中期核心组合和关键羁绊节点。
- 最终阵容、替补及目标人口。
- 核心追星目标。
- 替换条件和替换后的站位、装备、名单更新规则。

第一阶段只支持少量确定的替换，不实现完全自由转阵容。替换需确认新单位能上场且收益成立，再处理旧单位；严禁先卖核心再尝试不确定的购买或拖动。

非最终名单中的过渡卡必须进入统一保护规则，否则战阶段清理会将其当杂卡出售。系统自动上阵单位也应先识别、估值，再决定是否回收，避免无条件用弱单位替换更强的临时战力。

### 6.4 准备阶段按动作预算编排

当前固定15秒预留不随上阵、装备数量调整；上阵完成后的续跑也不主动补上新购单位。`_try_last_seconds_deploy()` 虽存在，但当前棋局代码搜索未发现调用点，不能视为已经生效的最后补位保障。

建议循环为：

1. 识别阶段和符咒中断。
2. 处理现有商店的高价值目标。
3. 如存在空位、关键新单位或装备提升，优先完成部署。
4. 预算允许时执行一次升级或刷新。
5. 重新观察，根据新状态决定下一步。

时间预算包含开关商店、识别、拖动、动画确认和安全余量；使用实际耗时统计逐步校准。临近开战时只处理能在安全窗口内完成的关键动作，不临时启动整套上阵循环。

时间检查应下沉到刷新、购买及其恢复步骤前。当前首轮买卡不受15秒保护约束，刷新后的买卡链路也可能较长，不能只在外层循环检查时间。

已发出的动作必须完成有界确认，超时或阶段变化记录结果未明；不能为了赶时间跳过确认，也不能跨阶段继续旧点击。

## 7. P3：符咒、站位和后续能力

### 7.1 符咒按实际局势计算边际收益

`strategy/grigri.py` 已提供基础评分和羁绊关联，可继续复用。但 `lineup_bond_context()` 统计的是预设完整阵容，不是当前棋盘；多数符咒分数没有回合、血量或已选效果输入。

建议把基础分解释为先验偏好，再结合以下条件调整：

- 当前回合及预计还能兑现收益的回合数。
- 现有血量和即时战力需求。
- 实际已上场羁绊、纹章和距离下一档位的差距。
- 已有符咒的重复、叠加或互斥效果。
- 当前是否仍需要经验、额外经济或特定装备。

前40%规则可先保留作兼容基线。进一步刷新决策应比较已知选项价值、剩余刷新机会及操作时间；没有符咒概率资料时，不伪造精确期望收益。

新评分采用可解释规则后，再决定是否调整界面配置及帮助文本，避免沿用“实际收益”字样却仍只是静态偏好分。

### 7.2 站位从角色模板开始

第一步采用明确的主坦、输出、辅助站位模板，保证独立位置及特殊单位规则。第二步才考虑根据对手输出方向、控制范围等信息，在少量预设布局间切换。

对手识别失败时保持已有布局；不在最后几秒大规模换位；每次移动后更新实际位置和装备目标。站位优化不能以牺牲可靠上阵为代价。

### 7.3 暂不优先实施

- 全自动任意转阵容。
- 完整公共卡池与竞争人数推断。
- 未经核实的商店概率模型。
- 强化学习或不可解释的大规模权重调参。
- 为追求动作速度取消截图确认、异常处理或卡死检测。

这些能力依赖更完整的观察与样本，应排在基础买卖、装备和经济闭环之后。

## 8. 代码组织与接口建议

| 位置 | 建议职责 |
| --- | --- |

| `strategy/grigri.py` | 符咒基础评分与局势修正 |
| 新增纯策略模块，文件名待实施确定 | 买卖、预算、装备和替换决策，不截图、不点击 |
| `runtime/economy.py` | 商店观察、交易执行、结果确认 |
| `runtime/hand_operations.py` | 按明确决策执行拖动、出售和装备，并确认结果 |
| `runtime/round_state.py` | 局势识别、阶段及时间读取 |
| `script_task.py` | 真实入口编排、动作优先级和阶段中断 |
| `runtime/settings.py` | 识别阈值、安全时限与动作上限 |

建议纯策略接口接收观察快照、阵容计划和预算，返回动作类型、目标、原因、所需前置条件及预计花费。执行层在动作前用新截图核验前置条件，条件变化则放弃旧决策并重算。

动作结果至少区分成功、明确未发生、暂时阻塞、结果未明和阶段结束。结果未明必须进入确认流程，不等同于可以再次点击的普通失败。

已有状态类可在审查后复用；避免长期维护两套棋盘名单或两个回合状态机。没有接入的旧逻辑需明确标识，待调用关系和测试证明无依赖后再整理。

### 9.4 实战评估方法

离线通过后，另行安排有明确范围的实战验证。按游戏版本、阵容、段位区间、运行目标和保段位开关分组，记录样本量，不混合不同条件比较。

建议先记录基线，再以同类条件分批对比；少量对局只用于发现流程问题，不足以证明胜率提升。

| 指标 | 用途 |
| --- | --- |
| 平均名次、前四率、后两名率 | 评价稳定保分能力 |
| 关键单位成型回合 | 评价买卡与运营效率 |
| 存在合法可用手牌时的空人口回合数 | 评价战力兑现能力 |
| 误卖、无确认重复付费、错误部署次数 | 评价安全底线 |
| 关键装备闲置及错误分配次数 | 评价装备收益 |
| 单回合动作耗时及超时次数 | 评价时间预算 |
| 每正常对局耗时、实测币增量与总占用时间 | 评价刷币效率 |

保段位主动退出局单独记录，不能混入正常对局平均名次。计算刷币效率时应计入真实总耗时；满币上限和剩余可获得额度会影响结果，不能只比较局数。

安全验收要求所有已知误卖和重复消费反例通过回归，实测一旦出现未经确认的重复付费或关键误卖就暂停该策略扩展。性能与胜率目标在取得基线后设定，不预先承诺固定提升百分比。

## 10. 必须保留的项目边界

- 不取消设备卡死检测；同一阶段不能因识别成功或重复点击无限续期。
- 经验扣款未确认时保留本回目停止重复购买的保护，不跨阶段续点。
- 新增动作均遵守回合、阶段、符咒中断、时间预算和确认时限。
- 不因策略优化从任意截图推断整局结算；必须确认结算并回到稳定大厅才计次。
- 保留闲时整局让位、满币双帧确认、周停刷、配置隔离和保段位退出计数。
- 不改动现有手动执行例外与调度语义；相关规则以当前代码、`AGENTS.md` 和维护文档为准。
- 局内决策状态驻留运行时，不逐帧写用户配置；新增显式配置保存仍遵守增量合并和文件锁要求。
- 遥测只记录决策需要的数据，不记录凭据；截图采集、保留范围和实战操作另行明确。
- 不引入私有业务模块、授权实现或其他项目未经审查的修改。

## 11. 分阶段完成标准

1. **P0完成**：阵容站位合法；刷新结果未明不会直接再次付费；满手不会按位置盲卖重要阵容卡；相关安全回归通过。
2. **P1完成**：买卖共享同一价值体系；状态缺失有明确降级；发现与装备按实际需求选择；关键场景可以用离线输入解释和复现。
3. **P2完成**：升级、刷新和储备不再仅由等级决定；过渡卡不会被清理误卖；新获得的关键战力能在合法时间内上场；实测流程稳定。
4. **P3完成**：符咒评分基于实际局势，有限站位调整可验证；有足够分组样本评估收益，保留效果不明或退化策略的停用路径。
