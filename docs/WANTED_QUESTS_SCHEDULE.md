# 悬赏封印执行时间推后

2026-10-17 检查当前工作树发现：

1. `ScriptTask.next_run()` 用 05:00 划分上午轮次，05:00–06:00 完成前一轮后会直接跳到下午，漏掉当天上午安排。
2. 下午执行时间同时被用作轮次边界；若配置为 20:00，18:00–20:00 已完成新一轮悬赏后仍可能重复安排当天 20:00。
3. `set_next_run()` 默认启用共用服务时间；上午时间为非默认值时，计算出的当天下午目标会被改成次日上午。短成功间隔也可能截短显式目标。

修复后按游戏每日 06:00、18:00 刷新点确定下一轮：

| 本轮完成时间 | 下次执行时间 |
| --- | --- |
| 00:00 ≤ 时间 < 06:00 | 当天上午配置时间 |
| 06:00 ≤ 时间 < 18:00 | 当天下午配置时间 |
| 18:00 ≤ 时间 | 次日上午配置时间 |

上午字段为 `server_update_am`，默认 09:00；下午 `server_update_pm` 默认 18:00。刷新时间不等于执行时间；若希望刷新即执行，可将上午配置为 06:00、下午配置为 18:00。上午时间应位于 06:00–18:00 之前，下午时间应位于 18:00–当日结束；本次未新增配置范围限制，也未改写用户配置。

悬赏的上午、下午字段使用独立名称和专用帮助说明。上午显示“上午悬赏执行时间”，不显示通用的“非 09:00 则强制次日”提示。旧 `server_update` 隐藏并迁移到 `server_update_am`，不覆盖已设置的新字段；保存重载后保留新值。悬赏中 09:00 仅为上午默认值，没有特殊调度含义。

`WantedQuests.next_run()` 先在对应轮次的配置时间上独立叠加一次随机延迟，再调用 `set_next_run(..., server=False)`，避免共用强制时间和 `delay_date` 覆盖结果。随机延迟按现有 `float_time` 从 0 至配置秒数抽取；设置为零时不抽取。配置层对悬赏显式目标保留精确值，不重复抽取，不取目标与成功间隔的最小值。手动指定的时间保持精确。其他任务行为保持原样，包括先前的麒麟阴界修复。

通用调度层同时直接排除 `wanted_quests`：即使其他调用方保留 `server=True`，也不应用通用的强制次日时间或额外随机延迟。正常完成后仍由任务按上午完成→当天下午、下午完成→次日上午计算目标。

成功间隔、失败间隔和强制日期间隔 `delay_date` 已从悬赏界面 schema 隐藏。旧配置仍能加载和保存这些字段，但悬赏调度完全忽略它们：传入显式目标时保留目标；仅传成功或失败状态时，按调用时刻通过 `WantedQuestsScheduler.next_refresh_run(..., random_delay=True)` 计算下一轮早晚时间并抽取一次随机延迟。失败也安排下一轮，不再按失败间隔重试。任务与配置层共用同一个计算方法，其他任务的间隔字段与行为保持原样。
