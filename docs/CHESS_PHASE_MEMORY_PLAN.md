# 百鬼棋局跨阶段记忆执行方案

日期：2026-11-10。
状态：设计待实施；本次仅落地商店目标图像识别，未实施下面的记忆系统。
范围：当前工作树 `tasks/Chess/`，包括已有未提交修改；不以 HEAD 替代实际代码。
目标：让反击姑获鸟的持牌、运营目标和未完成动作连续穿过备、战、待及回目切换，优先解决买到不上、合成状态滞后和重复观察。先保持现有打法门槛，不承诺胜率提升。

## 1. 现有基础与实施边界

- `runtime/inventory.py` 的 CardInventory 已保存单局棋盘、手牌及材料账本；不能再建立第二份独立数量真相。
- `runtime/card_tracking.py` 在每回目首次备阶段扫描棋盘，购买、上阵、回收后局部核对。
- `runtime/counter_ubume.py` 已记录支出上界、寻香行获取状态，纯运营规则在 `strategy/counter_ubume.py`。
- `script_task.py` 是实际阶段入口。不能直接启用未接入的旧 state_loop 并假定行为相同。
- 新记忆只在当前对局的任务实例中保存，不写用户配置、不持久化鼠标坐标、不跨进程恢复。正常同实例闲时让位保留；新局、确认退出和任务销毁清空。
- 商店图片模式与记忆系统分开交付。记忆实施不得重新接入商店名称或羁绊 OCR。

## 2. 状态结构

拟新增 `runtime/memory.py`，提供 GameMemory、ObservationStamp、PendingIntent、PendingTransaction。名称为拟议接口，当前不存在。

| 状态 | 保存内容 | 更新和失效规则 |
| --- | --- | --- |
| 对局上下文 | game_id、回目、阶段、阶段序号 | 稳定识别后切换；暂时识别不到不是新局 |
| 观察证据 | 帧号、单调时间、回目、来源、confirmed/stale/unknown | 旧事实保留但降低可用性，不用新一帧漏识别抹去 |
| 持牌引用 | 引用现有 CardInventory；按棋盘位置区分双久次良 | 合成、买卖、回收、上阵使受影响部分变脏并核对 |
| 运营目标 | 升六、六阶追鸟、升七、补第二三星、升八、八阶补齐 | 根据已确认事实推进；证据冲突先核对，不凭旧目标继续花钱 |
| 动作待办 | 目标角色/位置、触发原因、优先级、允许阶段、依赖和阻塞原因 | 按语义键去重；每次执行前重新找卡和检查前提 |
| 交易记录 | 动作编号、类型、点击前金币/等级、回目/阶段、预计费用、确认状态 | 一次点击一次登记；未确认不重复点击，不因换阶段释放支出预留 |
| 商店观察 | 商店版本、各槽目标身份、图像特征、观察时间 | 刷新/自然换店/遮挡/切换阵容失效；重新开店先验画面 |

手牌坐标是临时观察结果，不能当作卡牌永久身份。待上阵请求保存角色和目标位置；真正拖动前重定位。不要用累计买入次数代替当前持有量，不把未知卡当作空位。

## 3. 阶段切换协议

1. 确认回目和阶段变化，记录一次事件；保持现有稳定帧确认及总超时。
2. 保留持牌事实、战略目标和动作意图；旧画面坐标、可点击性及商店可见性立即失效。
3. 未完成交易进入待核对，不把未收到确认当作未点击。跨阶段收入可能混入余额，不能仅凭余额差证明上一笔成功。
4. 按当前阶段合法性筛选待办，重新核对前置条件，再执行一项原子动作。
5. 确认结果后更新现有账本及证据版本，撤销或生成相关待办；失败保留原因并有界重试。

| 阶段 | 优先处理 | 不允许 |
| --- | --- | --- |
| 备 | 弹窗；必要交易/棋盘核对；核心补阵和合成升级；装备；运营 | 用过期坐标拖动、空位未确认时强行交换 |
| 战/待 | 交易核对、合法商店购买与经验/刷新；登记下一备阶段待办 | 上阵、装备、跨阶段续点未确认经验 |
| 鬼/未知 | 原有特殊处理或观察，保存意图 | 将未知阶段视为可购买 |

保持最后3秒不启动新动作。已经点击的交易可以观察确认，但不能再次点击。等待和重试不能清空设备卡死计时；另按真实进展维持固定总超时。

## 4. 反击姑获鸟的连续运营

保持当前规则：六阶前不付费刷新，经验扣款后至少50；六、七阶经验和刷新扣款后至少31；买阵容牌仍按现有可负担规则，不把运营留钱线套到买牌。

- 六阶前：自然商店买体系牌，登记补阵；经验达到六阶时生成“新人口核对/补位”待办。
- 六阶：围绕实际持有量追姑获鸟；差材料可提高买牌优先级，但不能推断场上已三星。
- 场上姑获鸟经图像确认三星：记录达标证据，转升七。短暂遮挡保留事实，但涉及花钱时若有冲突必须先修复证据。
- 七阶：补第二张二星久次良；场上至少两个已确认三星且含鸟后转升八。
- 八阶：补荒骷髅及其余目标；全部达标后停止无效刷新。
- 寻香行替河童：依次记录回收待确认、寻香行上阵待确认、过渡卡可清理。没确认上阵成功前不能卖掉过渡战力。
- 双久次良用两个位置区分；七阶前第二只保留待办但标记等级未满足，不能阻塞其他运营。

典型过程：战阶段买鸟 → 交易确认 → 同名场上单位标记待核对 → 登记补阵/升星核对 → 下次备阶段新截图核对 → 更新真实星级 → 再决定继续刷新或买经验。阶段变化不丢掉中间步骤。

## 5. 商店记忆与识别边界

本次已实施：只加载当前阵容及替补商店图像，彩色模板匹配和原灰度发光兜底均属于图像路径。没有命中返回“未匹配目标卡”，不再调用名称或羁绊 OCR，不声称已认出非目标牌。金币、阶数、倒计时的数字 OCR 保留。

当前缓存仅复用同一帧。后续跨帧复用需单独实施：

- 对五格独立保存身份及特征；新帧确认稳定且区域未变才复用。
- 买入后作废受影响槽位；动画影响其他格时一并作废，不机械地只作废一格。
- 已发起刷新立即作废旧身份；等待新商店稳定后识别，不能用缓存证明刷新成功。
- 自然换店、回目切换和重新开店先验证画面。商店版本变化不要求五格名字不同。
- 身份缺失只说明未匹配目标卡，不能单独证明购买成功；扣款、同阶段/回目及商店可见性仍必须核对。
- 未确认交易和阶段切换的安全保护优先于缓存命中。

## 6. 分步实施与验收

### M1：统一观察生命周期

新增内存状态对象，接入新局重置和稳定阶段事件；为现有账本添加证据版本，不改买卖策略。接入 `script_task.py`、`card_tracking.py`。

验收：备→战→待→下一回目保留确认事实；暂时漏识别不删除单位；新局清空；双久次良、同实例暂停恢复不串状态；没有新增配置写盘。

### M2：可恢复待办与交易衔接

将战阶段购牌、升级解锁、替换和合成核对统一登记。接入 `counter_ubume.py`、`economy.py`、`hand_operations.py`。逐步迁移分散 pending 字段，过渡期保持单一写入入口，不能两套队列重复消费。

验收：每个语义待办至多执行一次；拖动中切阶段、点击后跨阶段、动画遮挡后恢复都先核对；未确认付费不重试；不合法阶段不执行；受等级阻塞待办不饿死其他动作。

### M3：运营目标与商店版本

纯策略只消费已确认快照；加入运营目标和理由日志。再实现按槽位变化的商店跨帧复用，分别验证正确性和耗时。

验收：九张材料不等于场上三星；备战区三星不触发升阶；已达标不因一帧漏识别反复切策略；旧商店不跨刷新复用；同名刷新、购买动画和自然换店不漏处理。

### M4：回放和实战评估

拟新增 `dev_tools.test_chess_phase_memory`，使用事件序列及可重复截图，不启动设备。至少覆盖上述场景，并增加阶段识别抖动、余额延迟、交易期间结算收入和任务异常退出。

分层计时：截图、五格识别、库存核对、买牌确认、补阵、装备、刷新、动画等待。报告预热后的中位数/P95、样本数、目标召回率/误买数，以及已购核心在下一备阶段的上阵完成率。不能拿单张模板耗时代表整轮耗时。

离线门禁：chess_phase_memory（新增后）、chess_phase_controls、chess_action_priority、chess_counter_ubume、chess_inventory、chess_unlisted_hand、chess_wait_economy、chess_performance、chess_p0、chess_shop、chess_runtime_safety、chess_idle、chess_exit、chess_season、chess_grigri，以及 config_template、task_startup、server_startup。

每阶段单独评审和验证。真实截图不足时明确未验证的光效/缩放；离线通过不能宣称胜率或整局效率提升。保持原来的卡死检测、交易保护和闲时退出规则。
